Software engineering · lecture 02

Same four activities. Different shapes. And change always comes.

Every software project does four things: decide what to build, build it, check it, and change it later. A process model is the shape a team arranges those four things into. This lecture compares three shapes. Then it asks how a process can survive change without wasting money.

The running example is the hotel booking app from Lecture 1. Hotel examples (🏨) are illustrations to help you remember; they are not slide content. The slide wording sits in blue “From the slides” boxes, and every section has a 📄 tag pointing back to the original file.

01 · The software process
📄 Slide 2

A process is the recipe for building software

A software process is the set of activities a team follows to build a software system. The slide calls it structured: the activities have a purpose and an order. You don't just open an editor and start typing.

There are many different software processes. But all of them include the same four activities. You met them in Lecture 1. Here they are again, in the slide's exact words.

FROM THE SLIDES

A structured set of activities required to develop a software system.

Many different software processes but all involve:

  • Specification – defining what the system should do;
  • Design and implementation – defining the organization of the system and implementing the system;
  • Validation – checking that it does what the customer wants;
  • Evolution – changing the system in response to changing customer needs.

A software process model is an abstract representation of a process. It presents a description of a process from some particular perspective.

Flip each card. The term is on the front, the definition on the back.

Two words in that last definition need explaining. Abstract means simplified on purpose: details are left out so the main idea is easy to see. A perspective is the angle you look from. So a process model is a simplified picture of a process, seen from one angle.

THINK OF IT LIKE…

One city, many maps. The metro map, the tourist map and the road map all show the same city. Each one leaves things out and shows the city from one perspective. A process model is a map of how software gets built. The three models in Part B are three different maps.

02 · Process descriptions
📄 Slide 3

Describing a process: what happens, in what order

When people describe a process, they usually talk about two things: the activities and the order of those activities. The slide gives two example activities. One is specifying a data model: a description of what data the system stores and how it links together. The other is designing a user interface: the screens, buttons and menus people use.

FROM THE SLIDES

When we describe and discuss processes, we usually talk about the activities in these processes such as specifying a data model, designing a user interface, etc. and the ordering of these activities.

Process descriptions may also include:

  • Products, which are the outcomes of a process activity;
  • Roles, which reflect the responsibilities of the people involved in the process;
  • Pre- and post-conditions, which are statements that are true before and after a process activity has been enacted or a product produced.

In plain words: a product is what an activity produces. A role says who is responsible. A pre-condition must be true before you start. A post-condition is true when you finish. Enacted just means “carried out”.

03 · Plan-driven vs agile
📄 Slide 4

Plan it all up front, or plan as you go

Processes fall into two big families. The difference is when the planning happens.

  • Plan-driven: everything is planned before the work starts. Progress is checked against that plan.
  • Agile: planning is incremental, which means it is done in small pieces, a bit at a time. Because of that, the process is easier to change when the customer's needs change.
FROM THE SLIDES

Plan-driven processes are processes where all of the process activities are planned in advance and progress is measured against this plan.

In agile processes, planning is incremental, and it is easier to change the process to reflect changing customer requirements.

In practice, most practical processes include elements of both plan-driven and agile approaches.

There are no right or wrong software processes.

Agile is backpacking: you know where you're heading, but you plan the next stop when you get there. Most real trips mix both: flights booked months ahead, days planned on the spot. Neither trip is “wrong”.

05 · Waterfall
📄 Slides 7–9

The waterfall: finish one phase, then the next

The waterfall model splits a project into separate, clearly named phases. Work flows down from one phase to the next, like water down a staircase. Step through the phases below. The arrows going back up are feedback: a problem found in a later phase sends you back to an earlier one.

The waterfall model rebuilt from slide 7

Requirements analysis and definition

Find out, together with the users, what the system must do and what limits it works within. Write it down as the specification.

The hotel needs online room search, booking and card payment for 350 rooms.

System and software design

Decide the overall structure: which parts the system has and how they connect.

A booking database, a website, and a link to the card-payment provider.

Implementation and unit testing

Write the code as separate units (small pieces of the program). A unit test checks one unit on its own.

Test the “calculate room price” code alone, before anything else uses it.

Integration and system testing

Integration joins the units into one system. System testing tests the whole system working together.

Search, booking and payment are joined and tested from start to finish.

Operation and maintenance

The system is installed and in real use. Maintenance means fixing problems and improving the system while people use it.

Guests book online; the team fixes bugs that the front desk reports.

FROM THE SLIDES

There are separate identified phases in the waterfall model:

  • Requirements analysis and definition
  • System and software design
  • Implementation and unit testing
  • Integration and system testing
  • Operation and maintenance

The main drawback of the waterfall model is the difficulty of accommodating change after the process is underway. In principle, a phase has to be complete before moving onto the next phase.

That last point is the key weakness. Accommodating a change means fitting it into the work. Each phase is meant to be finished before the next begins, so a late change forces you back up the staircase.

Waterfall problems, and where it still fits 📄 Slide 9

✗ The problem

  • Inflexible partitioning of the project into distinct stages makes it difficult to respond to changing customer requirements.
    • Therefore, this model is only appropriate when the requirements are well-understood and changes will be fairly limited during the design process.
    • Few business systems have stable requirements.

Partitioning = splitting the project into stages. Stable requirements = requirements that don't change.

✓ Where it fits

  • The waterfall model is mostly used for large systems engineering projects where a system is developed at several sites.
    • In those circumstances, the plan-driven nature of the waterfall model helps coordinate the work.

A systems engineering project builds a large system of hardware, software and people together. When teams in different places each build a part, one fixed plan keeps everyone in step.

THINK OF IT LIKE…

Water does not flow uphill. Building a house works the same way: once the foundation is poured and the walls are up, moving the kitchen to the other side means breaking work you already finished.

06 · Incremental development
📄 Slides 10–12

Incremental development: build, show, improve

You start with an outline description: a rough idea of the system. Then specification, development and validation run as concurrent activities. That means they happen side by side and feed each other. Each round produces a new version: first an initial version, then intermediate versions, then the final version.

Benefits 📄 Slide 11

💸

Cheaper to change

The cost of accommodating changing customer requirements is reduced.

The amount of analysis and documentation that has to be redone is much less than is required with the waterfall model.

💬

Easier feedback

It is easier to get customer feedback on the development work that has been done.

Customers can comment on demonstrations of the software and see how much has been implemented.

🚀

Useful software sooner

More rapid delivery and deployment of useful software to the customer is possible.

Customers are able to use and gain value from the software earlier than is possible with a waterfall process.

Problems 📄 Slide 12

👀 The process is not visible.

Managers need regular deliverables to measure progress. If systems are developed quickly, it is not cost-effective to produce documents that reflect every version of the system.

Deliverables = things a manager can check, like documents and reports. Cost-effective = worth the money it costs.

🧶 System structure tends to degrade as new increments are added.

Unless time and money is spent on refactoring to improve the software, regular change tends to corrupt its structure. Incorporating further software changes becomes increasingly difficult and costly.

Refactoring = reorganizing code to make it cleaner, without changing what it does.

THINK OF IT LIKE…

Writing an essay in drafts. You show each draft to your teacher and fix problems early, which is cheaper than rewriting a finished essay. But if you keep pasting in new paragraphs without ever reorganizing, the essay becomes a tangle. Refactoring is the reorganizing.

07 · Integration & configuration
📄 Slides 13–17

Don't build it. Reuse it and configure it.

This model is based on software reuse: using software that already exists instead of writing it again. The system is integrated (joined together) from existing components or whole application systems.

Ready-made application systems are sometimes called COTS, short for Commercial-Off-The-Shelf: software you buy ready-made, like a product off a shop shelf. Reused parts can be configured: you change their settings so they behave the way your users need, without rewriting them.

FROM THE SLIDES

Based on software reuse where systems are integrated from existing components or application systems (sometimes called COTS -Commercial-off-the-shelf) systems).

Reused elements may be configured to adapt their behaviour and functionality to a user's requirements.

Reuse is now the standard approach for building many types of business system.

Three types of reusable software 📄 Slide 14

Show more detail: the terms on these cards

A component framework is a platform that sets the rules for how software parts plug together. .NET (from Microsoft) and J2EE (Java's enterprise platform) are the two examples on the slide. A service standard is an agreed format for how services talk to each other. Remote invocation means calling code that runs on another computer, over a network.

Advantages and disadvantages 📄 Slide 17

✓ Advantages

  • Reduced costs and risks as less software is developed from scratch
  • Faster delivery and deployment of system

✗ Disadvantages

  • But requirements compromises are unavoidable, so system may not meet real needs of users
  • Loss of control over evolution of reused system elements

Two terms. A compromise means accepting something close to what you wanted, because the ready-made part doesn't do exactly that. Loss of control over evolution means someone else decides how the reused part changes: when it gets updates, which features it gains, or when it stops being supported.

THINK OF IT LIKE…

Furnishing a flat from a furniture store instead of hiring a carpenter. It's faster and cheaper. But the sofa comes in three sizes and none fits your wall exactly (a requirements compromise). And when the store stops selling that model, you can't buy matching chairs (loss of control).

08 · Coping with change
📄 Slides 18–19

Change isn't an accident. It's guaranteed.

The slide says change is inevitable in all large software projects: it will certainly happen. It comes from three directions.

💼

Business changes

Business changes lead to new and changed system requirements.

A new tax rule changes how invoices are calculated.

🧪

New technologies

New technologies open up new possibilities for improving implementations.

Phones gain tap-to-pay, so guests could pay by phone.

🖥️

Changing platforms

Changing platforms require application changes.

The hosting company retires the old server version.

A platform is what the software runs on: the hardware, operating system, browser or cloud service. Every change creates rework: redoing work you already did. So the real cost of a change is bigger than the new feature alone.

FROM THE SLIDES

Change is inevitable in all large software projects.

  • Business changes lead to new and changed system requirements
  • New technologies open up new possibilities for improving implementations
  • Changing platforms require application changes

Change leads to rework so the costs of change include both rework (e.g. re-analysing requirements) as well as the costs of implementing new functionality

09 · Reducing rework
📄 Slides 20–21

Two ways to make change cheaper

You can't stop change. But a process can make change cost less, in two ways.

🔭 Change anticipation

The software process includes activities that can anticipate possible changes before significant rework is required.

  • For example, a prototype system may be developed to show some key features of the system to customers.

Plain words: spot the change early, while it is still cheap. To anticipate is to see something coming.

🧘 Change tolerance

The process is designed so that changes can be accommodated at relatively low cost.

  • This normally involves some form of incremental development. Proposed changes may be implemented in increments that have not yet been developed. If this is impossible, then only a single increment (a small part of the system) may have [to] be altered to incorporate the change.

Plain words: when change arrives, it only hurts a little. To tolerate is to cope without damage.

Two techniques for changing requirements 📄 Slide 21

TechniqueWhat it is (slide wording)Supports
System prototypingA version of the system or part of the system is developed quickly to check the customer's requirements and the feasibility of design decisions.change anticipation
Incremental deliverySystem increments are delivered to the customer for comment and experimentation.change avoidance change tolerance

Feasibility means whether something can actually work. Prototyping lets you test a design idea before you commit to it. Both techniques get their own sections next: §10 prototyping and §11 incremental delivery.

WORDING NOTE

Slide 20 says change anticipation; slide 21 says change avoidance. They name the same idea: catch the change early, so you avoid expensive rework. Older editions of the Sommerville textbook used the name “change avoidance” for it. In an exam answer, quote each slide's own wording.

THINK OF IT LIKE…

Rain on a holiday. Anticipation: check the forecast and pack an umbrella before you leave. Tolerance: wear a jacket that doesn't care whether it rains.

10 · Prototyping
📄 Slides 22–26

Prototypes: try it before you build it

A prototype is an early, rough version of a system. You use it to show ideas and to try out design options before you build the real thing.

FROM THE SLIDES

A prototype is an initial version of a system used to demonstrate concepts and try out design options.

A prototype can be used in:

  • The requirements engineering process to help with requirements elicitation and validation;
  • In design processes to explore options and develop a UI design;
  • In the testing process to run back-to-back tests.
📋

Requirements engineering

Elicitation means drawing out what users need. Users often can't say what they want until they see something. Validation here means checking that the requirements are right.

🎨

Design

Explore different design options and develop the UI (user interface) design before committing to one.

🧪

Testing

Back-to-back tests: run the same tests on the prototype and on the real system, then compare the results. A difference points to a possible bug.

Benefits of prototyping 📄 Slide 23

🙂 Improved system usability 🎯 A closer match to users' real needs 📐 Improved design quality 🔧 Improved maintainability ⏱️ Reduced development effort

Usability = how easy the system is to use. Maintainability = how easy it is to change later (the most critical attribute of good software from Lecture 1).

How prototypes are built 📄 Slide 25

FROM THE SLIDES · PROTOTYPE DEVELOPMENT
  • May be based on rapid prototyping languages or tools
  • May involve leaving out functionality
    • Prototype should focus on areas of the product that are not well-understood;
    • Error checking and recovery may not be included in the prototype;

A prototype is built for speed, so it leaves things out on purpose. It focuses on the parts nobody understands well yet, because that is where you learn the most.

Show more detail: functional vs non-functional, error checking

Functional requirements say what the system does: “guests can book a room”. Non-functional requirements say how well it does it, such as reliability (works without failing) and security (keeps attackers out). A prototype focuses on the first kind.

Error checking and recovery is the code that catches mistakes (a wrong date, a lost connection) and gets the system back to a safe state. Prototypes may skip it. Rapid prototyping languages or tools are tools made for building something that works quickly, not something that lasts.

Throw-away prototypes 📄 Slide 26

Prototypes should be discarded after development, because they are not a good basis for a production system: the real system that customers rely on every day. Tap through the slide's reasons.

An architect's cardboard model of a building. It's perfect for showing the client and trying different layouts. But nobody moves into the cardboard model. Once it has done its job, you build the real thing properly.

11 · Incremental delivery
📄 Slides 27–31

Incremental delivery: ship it in slices

Instead of handing over the whole system at once, you deliver it in increments: slices that each contain part of the features. The most important features go first. Once work on a slice starts, its requirements are frozen: locked, no more changes. Requirements for later slices can still change.

FROM THE SLIDES

Rather than deliver the system as a single delivery, the development and delivery is broken down into increments with each increment delivering part of the required functionality.

User requirements are prioritised and the highest priority requirements are included in early increments.

Once the development of an increment is started, the requirements are frozen though requirements for later increments can continue to evolve.

Incremental development vs incremental delivery 📄 Slide 28

The two names sound alike, but they are different. The difference is whether the increment goes to real end-users, or is only evaluated by someone standing in for them.

Incremental developmentIncremental delivery
Develop the system in increments and evaluate each increment before proceeding to the development of the next increment;Deploy an increment for use by end-users;
Normal approach used in agile methods;More realistic evaluation about practical use of software;
Evaluation done by user/customer proxy.Difficult to implement for replacement systems as increments have less functionality than the system being replaced.

A proxy is someone who stands in for the real users, such as a customer representative. To deploy is to put into real use. A replacement system replaces an old system that people already use; they won't switch to a slice that does less than what they already have.

Advantages and problems 📄 Slides 30–31

✓ Incremental delivery advantages

  • Customer value can be delivered with each increment so system functionality is available earlier.
  • Early increments act as a prototype to help elicit requirements for later increments.
  • Lower risk of overall project failure.
  • The highest priority system services tend to receive the most testing.

✗ Incremental delivery problems

  • Most systems require a set of basic facilities that are used by different parts of the system.
    • As requirements are not defined in detail until an increment is to be implemented, it can be hard to identify common facilities that are needed by all increments.
  • The essence of iterative processes is that the specification is developed in conjunction with the software.
    • However, this conflicts with the procurement model of many organizations, where the complete system specification is part of the system development contract.
Show more detail: the terms in these lists

Top services get the most testing because they ship in the first increment, so they are tested again every time a later increment is added.

Basic facilities are shared services that many parts need, like login or database access. Iterative means working in repeated rounds. In conjunction with means together with. The procurement model is how an organization buys a system: often it signs a contract that must contain the complete specification up front. That clashes with writing the specification as you go.

THINK OF IT LIKE…

A TV series instead of one long film. Viewers watch episode 1 while later episodes are still being written. Once an episode is being filmed, its script is locked (frozen). Later scripts can still change, based on what viewers say.

12 · Lecture recap
📄 Slides 1–32

Lecture recap

Key points

  1. Every software process includes specification, design and implementation, validation and evolution. A process model is an abstract representation of a process, from one perspective. 📄 S2
  2. Process descriptions cover activities and their order. They may add products, roles, and pre- and post-conditions. 📄 S3
  3. Plan-driven: plan all activities in advance; measure progress against the plan. Agile: plan incrementally; easier to change. Most real processes mix both, and no process is right or wrong. 📄 S4
  4. Waterfall is plan-driven with separate phases. Its main drawback is handling change once underway. Use it only when requirements are well understood; it is mostly used for large systems engineering projects at several sites. 📄 S6–9
  5. Incremental development interleaves specification, development and validation. Benefits: cheaper change, easier feedback, earlier delivery. Problems: the process is not visible, and structure degrades without refactoring. 📄 S10–12
  6. Integration and configuration builds systems from reusable software: COTS application systems, object collections for frameworks like .NET or J2EE, and web services. It is cheaper and faster, but brings requirements compromises and loss of control over reused parts. 📄 S13–17
  7. Change is inevitable. Cost of change = rework + new functionality. Reduce it with change anticipation (e.g. prototyping) and change tolerance (e.g. incremental development). 📄 S19–21
  8. A prototype demonstrates concepts and tries design options, in requirements engineering, design and testing. It focuses on poorly understood areas and functional requirements, and it should be thrown away afterwards. 📄 S22–26
  9. Incremental delivery ships prioritised increments to real end-users. An increment's requirements freeze once its development starts. 📄 S27–31

1. Embedded systems

This is a system where the software controls a hardware device and is embedded in that device.

Show more detail

How does it work? An embedded system receives input, processes it according to programmed rules, and produces an output by controlling hardware.

🧭⌚🎵🚦🏥📱🎮📶📹🤖📀🧺🚆☎️🚗

Pictured on slide 5: a GPS unit, watch, music player, traffic light, medical scanner, phone, game console, router, camcorder, robot, DVD player, washing machine, train, telephone and car.

For example, a washing machine controller:

  1. Receives input from the user, such as the selected washing program.
  2. Reads sensors, such as water-level sensors.
  3. Determines what action should happen next.
  4. Controls the motor, water valves, and other components.

Issues in embedded systems include:

  • Physical size: Embedded devices often have limited space for processors, memory, batteries, and other components. Software may need to operate within these hardware limitations.
  • Responsiveness: The software must respond within an acceptable time. For example, a control system may need to react quickly when a sensor detects a dangerous condition.
  • Power management: Many embedded systems use batteries or limited power sources. Their software must avoid wasting energy and may need to control when components are active.

Note: Embedded software must work correctly while respecting hardware, timing, and power limitations. 📄 T1 slides 5–7

🗄️

2. Information systems

This is a system whose primary purpose is to manage and provide access to a database of information.

Show more detail

Consider a hospital patient information system. It may store patient details, appointments, diagnoses, treatment history, and prescriptions. Users can search for records, update information when authorized, and generate reports.

Issues in information systems include:

  • Security: Security protects the system against unauthorized access, alteration, or destruction.
  • Usability: Usability refers to how easily people can learn and use the system.
  • Privacy: Privacy concerns how personal information is collected, accessed, shared, and used.
  • Maintaining data integrity: Data integrity means keeping information accurate, consistent, and protected against improper changes. Example: a patient's medication record should not accidentally be replaced with another patient's prescription.

Note: An information system is not successful merely because it stores data. The data must also be secure, usable, private, and accurate. 📄 T1 slides 8–9

3. Sensor-based data collection systems

This is a system whose primary purpose is to collect data from a set of sensors and process that data in some way.

Show more detail

A sensor measures something in the physical world and converts it into a form that a computer can use. Example: Temperature sensors measuring air temperature.

Key requirements of such systems:

  • Reliability, even in hostile environmental conditions, such as extreme temperatures, rain, wind,… etc.
  • Maintainability.

This assignment develops a computerized system to help restaurant employees coordinate their activities and improve their services, and for the management to track business growth and create future plans.

The goal for this assignment is to introduce automation in privately-owned restaurants, that is, small to medium-sized establishments. Typical problems restaurant personnel are facing include:

  • Coordination of their work activities.
  • Anticipating and handling periods of low/high patron traffic.
  • Lowering operating costs, and increasing efficiency/productivity and profits.
Today: the pen-and-paper restaurant (slides 52–54)

Many restaurants are still operated using pen and paper methods, with little or no automation. Patrons enter the facility to be greeted by a host, who often times has a “dry erase” diagram of the tables, maintained on a blackboard. The host can see the status of the tables based on whether or not they or someone else physically updates the diagram.

Slide 52 shows a floor plan with 55 numbered tables arranged in six zones.

Once seated a waiter tends to the customers by jotting down the orders onto a piece of carbon paper and delivers it to the kitchen for proper food preparation.

The waiter then has to periodically check back to find out when the meal is ready. When the food is done, the piece of carbon paper is saved for proper record keeping by the management.

This “old fashion” system works but yields a large amount of tab receipts, wastes a lot of time and is simply out-of-date. In old fashion systems, waiters have to carry pads around to take orders, always have a working pen and be sure to keep each bill organized and “synchronized” with the proper table.

The proposed touch-screen system (slides 55–56)

By using a touch screen the restaurant staff can quickly and efficiently log in and complete the desired task.

When a waiter logs in, they are greeted with a floor status screen in which their assigned tables are colored in. Their tables are colored according to status; green is open, yellow is occupied, red is dirty. At this point a waiter can select a table to view its tab/ receipt.

Once a table is selected, the staff can choose from a number of options. If they select to add an item to the table's tab, they are presented with various categories of food items offered. Here they can select the appropriate category and then find the desired item. They are then returned to that table's screen where they can choose to perform another task or logout.

This saves the waiter from walking back and forth to the kitchen to deliver and check up on food orders. Orders placed by wait-staff using the computer terminals on the restaurant floor are displayed to the kitchen staff through a queue, i.e., on a first-in, first out basis.

The screen mock-up on slides 55–56 labels its legend “Ready”, “Occupied”, “Dirty” and “Assigned to Other Waiters”.

02 · Requirements engineering
📄 Slides 3–4

Requirements engineering: finding out what to build

Software specification is also called requirements engineering (RE). It works out two things: the services the customer needs (what the system does) and the constraints (the limits on how it works and how it is built).

FROM THE SLIDES

The process of establishing the services that a customer requires from a system and the constraints under which it operates and is developed.

Requirements engineering process

  • Requirements elicitation and analysis
    • What do the system stakeholders require or expect from the system?
  • Requirements specification
    • Defining the requirements in detail
  • Requirements validation
    • Checking the validity of the requirements

Elicitation means drawing information out of people, for example by interviewing them or watching them work. Analysis means making sense of what you heard. Stakeholders are everyone with an interest in the system (§5 covers them). Validity means the requirements are correct and really describe what is needed.

The requirements engineering process rebuilt from slide 4

Find out what the stakeholders require or expect. Talk to them, watch how they work, study existing systems. The result is a description of the system and its setting.

📄 Slide 5

A requirement can be one line or a whole page

Others are detailed enough to be almost mathematical. The slide says this range is unavoidable, because requirements do two different jobs.

04 · User vs system requirements
📄 Slides 6–8

User requirements vs system requirements

Requirements are written at two levels. User requirements are for the customer: plain language plus diagrams. System requirements are the detailed, structured version that says exactly what must be built. Because they are precise, they can become part of the contract between the client (who buys the system) and the contractor (who builds it). The two Mentcare boxes in §3 are a user requirement (1) and its system requirements (1.1 to 1.5).

FROM THE SLIDES
  • User requirements: Statements in natural language plus diagrams of the services the system provides and its operational constraints. Written for customers.
  • System requirements: A structured document setting out detailed descriptions of the system's functions, services and operational constraints. Defines what should be implemented so may be part of a contract between client and contractor.

Natural language means ordinary human language, like English, rather than code or formulas. Operational constraints are limits on how the system runs. In slide 7's example, “17.30” is 5:30 pm, and a dose unit is a strength such as 10mg or 20mg.

Notice the patients. They never log in, but the system holds their private data, so they are clearly affected. A requirement such as patient privacy exists because of them.

THINK OF IT LIKE…

Planning a wedding. The couple matters most, but so do the guests, both families, the caterer, the venue owner, and even the neighbours who care about noise after midnight. Forget one of them and the plan runs into trouble.

06 · Agile and requirements
📄 Slide 11

Agile teams: less paper, more stories

Agile methods (Lecture 2, §3) plan in small steps. Many agile teams think a big, detailed requirements document is wasted effort: requirements change so fast that the document is always out of date. Instead they do requirements engineering incrementally, a bit at a time, and often write requirements as user stories.

FROM THE SLIDES
  • Many agile methods argue that producing detailed system requirements is a waste of time as requirements change so quickly.
  • The requirements document is therefore always out of date.
  • Agile methods usually use incremental requirements engineering and may express requirements as ‘user stories’.
  • This is practical for business systems but problematic for systems that require pre-delivery analysis (e.g. critical systems) or systems developed by several teams.

A user story is a short, everyday description of one thing a user wants to do. 🏨 For example: “As a hotel guest, I want to cancel my booking online, so I don't have to phone the hotel.” (The slide gives no example; this one is an illustration.)

✓ Practical for

  • Business systems

Their requirements change often, and a small mistake is fixed in the next increment.

✗ Problematic for

  • Systems that require pre-delivery analysis (e.g. critical systems)
  • Systems developed by several teams

Pre-delivery analysis means checking the system thoroughly before anyone uses it, like the insulin pump from Tutorial 1. Several teams also need one shared, written description to stay in step.

THINK OF IT LIKE…

A family planning a weekend uses sticky notes on the fridge: quick, easy to change. A hospital building a new wing uses a thick, signed specification, because many contractors must agree and mistakes are dangerous.

07 · Three kinds of requirement
📄 Slides 12–15

Functional, non-functional, and domain

This is the heart of the lecture. Requirements come in three kinds.

  • Functional: what the system does. Its services, how it reacts to inputs, how it behaves in particular situations. It can even say what the system must not do.
  • Non-functional: limits on those services, such as how fast, which standards, which development process. These usually apply to the whole system, not one feature.
  • Domain: constraints that come from the domain the system works in: its field, such as medicine, banking or aviation.
FROM THE SLIDES
  • Functional requirements
    • Statements of services the system should provide, how the system should react to particular inputs and how the system should behave in particular situations.
    • May state what the system should not do.
  • Non-functional requirements
    • Constraints on the services or functions offered by the system such as timing constraints, constraints on the development process, standards, etc.
    • Often apply to the system as a whole rather than individual features or services.
  • Domain requirements
    • Constraints on the system from the domain of operation

Functional requirements up close 📄 Slides 14–15

FROM THE SLIDES
  • Describe functionality or system services.
  • Depend on the type of software, expected users and the type of system where the software is used.
  • Functional user requirements may be high-level statements of what the system should do.
  • Functional system requirements should describe the system services in detail.

Example: Mentcare system's functional requirements

  • A user shall be able to search the appointments lists for all clinics.
  • The system shall generate each day, for each clinic, a list of patients who are expected to attend appointments that day.
  • Each staff member using the system shall be uniquely identified by his or her 8-digit employee number.

Notice the word “shall” in every example. Requirements use “shall” to mean “must”. Keep the first example in mind; §8 shows how one word in it causes trouble.

THINK OF IT LIKE…

A car. Functional: it drives, brakes and plays the radio. Non-functional: it reaches 100 km/h in 9 seconds, uses 5 litres per 100 km, and passes crash tests. Domain: it must follow the road rules of the country it is sold in, like driving on the left in the UK.

09 · Non-functional requirements
📄 Slides 18–22

Non-functional requirements: how well, not what

Non-functional requirements (NFRs) describe properties of the system and constraints on it. Properties are things like reliability, response time and storage needs. Constraints include what the input/output devices can do, and how data is represented.

FROM THE SLIDES
  • These define system properties and constraints e.g. reliability, response time and storage requirements. Constraints are I/O device capability, system representations, etc.
  • Process requirements may also be specified mandating a particular IDE, programming language or development method.
  • Non-functional requirements may be more critical than functional requirements. If these are not met, the system may be useless.

I/O devices are input and output hardware: keyboards, screens, card readers, printers. Process requirements constrain how the system is built. Mandating means requiring by rule. An IDE (Integrated Development Environment) is the program developers write code in. “More critical” because a booking system that offers every feature but takes two minutes per click is useless.

How NFRs shape the system 📄 Slide 20

FROM THE SLIDES · NON-FUNCTIONAL REQUIREMENTS IMPLEMENTATION
  • Non-functional requirements may affect the overall architecture of a system rather than the individual components.
    • For example, to ensure that performance requirements are met, you may have to organize the system to minimize communications between components.
  • A single non-functional requirement, such as a security requirement, may generate a number of related functional requirements that define system services that are required.
    • It may also generate requirements that restrict existing requirements.

The architecture is the overall structure: which big parts exist and how they connect. A functional requirement usually lives in one part. An NFR like “fast” can force you to reorganize all of them. 10 · Goals & metrics
📄 Slides 23–25

“Easy to use” is a wish. A number is a requirement.

NFRs are hard to state precisely, and a vague one is hard to verify (prove it was met). So the slide separates two things. A goal is a general intention, like “easy to use”. A verifiable non-functional requirement uses a measure that can be objectively tested: anyone who tests it gets the same answer. Goals still help, because they tell developers what users intend.

FROM THE SLIDES
  • Non-functional requirements may be very difficult to state precisely and imprecise requirements may be difficult to verify.
  • Goal
    • A general intention of the user such as ease of use.
  • Verifiable non-functional requirement
    • A statement using some measure that can be objectively tested.
  • Goals are helpful to developers as they convey the intentions of the system users.
Example: usability requirements 📄 Slide 24
GOAL

The system should be easy to use by medical staff and should be organized in such a way that user errors are minimized.

Neither “easy” nor “minimized” comes with a number, so two testers could disagree and nobody can prove it was met.

TESTABLE NON-FUNCTIONAL REQUIREMENT

Medical staff shall be able to use all the system functions after four hours of training. After this training, the average number of errors made by experienced users shall not exceed two per hour of system use.

The highlighted parts are measures. Train staff for four hours, count their errors per hour, and you have a clear pass or fail.

11 · Requirements change
📄 Slides 26–29

Requirements will change. Plan for it.

Requirements are never finished. The world around the system keeps moving, the people paying for it want different things from the people using it, and big user groups disagree among themselves.

🌦️

The environment changes

New hardware, links to other systems, new business priorities, new laws and regulations.

💳

Payers ≠ users

Customers set requirements from budget and policy. These can clash with what end-users need.

👥

Many users, many wishes

A large user community has conflicting priorities, so the requirements are a compromise.

FROM THE SLIDES · CHANGING REQUIREMENTS
  • The business and technical environment of the system always changes after installation.
    • New hardware may be introduced, it may be necessary to interface the system with other systems, business priorities may change (with consequent changes in the system support required), and new legislation and regulations may be introduced that the system must necessarily abide by.
  • The people who pay for a system and the users of that system are rarely the same people.
    • System customers impose requirements because of organizational and budgetary constraints. These may conflict with end-user requirements and, after delivery, new features may have to be added for user support if the system is to meet its goals.
  • Large systems usually have a diverse user community, with many users having different requirements and priorities that may be conflicting or contradictory.
    • The final system requirements are inevitably a compromise between them and, with experience, it is often discovered that the balance of support given to different users has to be changed.

Installation = putting the system into use. To interface with another system = to connect and exchange data with it. Legislation = laws. A diverse user community = many different kinds of users.

12 · Requirements management
📄 Slides 30–32

Requirements management: keep track of every change

Requirements management is the work of controlling changing requirements, both during RE and while the system is being built. New requirements keep appearing, even after the system goes live. So you need to track each requirement, record which requirements depend on which, and have a formal way to propose changes.

FROM THE SLIDES
  • Requirements management is the process of managing changing requirements during the requirements engineering process and system development.
  • New requirements emerge as a system is being developed and after it has gone into use.
  • You need to keep track of individual requirements and maintain links between dependent requirements so that you can assess the impact of requirements changes. You need to establish a formal process for making change proposals and linking these to system requirements.

Dependent requirements rely on each other: change one and the other may break. Assessing the impact means working out what else a change affects.

FROM THE SLIDES · KEY POINTS (SLIDE 33)
  • Requirements for a software system set out what the system should do and define constraints on its operation and implementation.

Part B · Process models, the tutorial's version 📄 T2 slides 11–53

A process model is a simplified representation of how software development activities are organized. Each model offers a different approach to managing requirements, design, implementation, and testing. The tutorial covers three: the waterfall model, incremental development, and reuse-oriented software engineering. Open each block for the tutorial's extra detail.

🌊 Waterfall in detail, with the university example (slides 14, 17–32)

The waterfall model takes the fundamental process activities of specification, development, validation, and evolution and represents them as separate process phases such as requirements specification, software design, implementation, testing. (Slide 14's picture labels five steps: Requirements Analysis, Design, Development, Testing, Maintenance.) Process type: plan-driven. All process activities must be planned and scheduled before starting work on them.

PhaseWhat the tutorial addsSlide
1. Requirements analysis and definitionThe system's services, constraints, and goals are established by consultation with system users. They are then defined in detail and serve as a system specification.18
2. System and software designAllocates the requirements to hardware/software systems by establishing an overall system architecture. Architecture describes the major components of the system and how they interact.19
3. Implementation and unit testingThe software design is realized as a set of programs or program units. A program unit is a relatively small, identifiable part of the software, such as a function, class, or module. Unit testing involves verifying that each unit meets its specification, and helps identify defects before individual components are combined. Example: a function that calculates a student's total registered credits could be tested independently. Possible tests: one course; several courses; a registration that exceeds the credit limit; invalid or missing input.20–21
4. Integration and system testingThe individual program units or programs are integrated and tested as a complete system to ensure that the software requirements have been met. After testing, the software system is delivered to the customer.22
5. Operation and maintenanceNormally (although not necessarily), the longest life cycle phase. The system is installed and put into practical use. The actual environment can expose problems not obvious during development, e.g. fine in a small test but slow when thousands of users use it at once. Maintenance: correcting errors not discovered earlier; improving the implementation of system units (e.g. optimizing a slow database query); enhancing services as new requirements are discovered.23–24

Each phase (slide 25): the result of each phase is one or more documents that are approved (“signed off”). The following phase should not start until the previous phase has finished.

Drawbacks (slides 26–28):

  1. Overlap: the software process is not a simple linear model but involves feedback from one phase to another. Documents produced in each phase may then have to be modified to reflect the changes made.
  2. Costly: because of the costs of producing and approving documents, iterations can be costly and involve significant rework. Producing, reviewing, and approving documents takes time and money; when requirements change, the team may need to repeat parts of this work.
  3. Freeze: therefore, after a small number of iterations, it is normal to freeze parts of the development, such as the specification, and to continue with the later stages. Problems are left for later resolution, ignored, or programmed around (quick coding solutions). This premature freezing may mean the system won't do what the user wants, and may lead to badly structured systems as design problems are circumvented by implementation tricks.
Worked example: a university registration system 📄 T2 slides 29–32

The team writes the requirements

The university requests three features: students can register for courses; students can view their timetables; students can see their grades. The team writes these requirements in a document.

The team freezes the requirements

After discussing the requirements a few times, the team decides: “We have enough information. Let's stop changing the requirements and start building the system.” This is called freezing the requirements.

The university discovers a missing feature

While the team is developing, the university says: “We also need students to be able to drop a course during the add/drop period.” The team realizes this requirement was not properly considered earlier.

The team handles the problem poorly

Instead of reviewing the design, the developers add a simple button that lets students drop a course, but the system does not correctly update the student's timetable and course-registration records. They continue without properly fixing it. The three possible responses to unresolved problems: left for later (“We will fix this in the future”), ignored, or programmed around (a quick coding solution instead of fixing the design).

What can go wrong

The system may not meet the user's needs: students can drop courses, but their registration records may not update correctly. The system may be poorly designed: the quick fix may create inconsistencies between different parts of the system, making future changes more difficult.

🔁 Incremental development in detail (slides 15, 33–40)

This approach interleaves the activities of specification, development, and validation. The system is developed as a series of versions (increments), with each version adding functionality to the previous version. Process type: agile, plan-driven, or both. It is based on developing an initial implementation, exposing it to user comment (feedback) and evolving it through several versions until an adequate system has been developed.

It reflects the way we solve problems: we rarely work out a complete solution in advance, but move toward one in a series of steps, backtracking when we realize we made a mistake. Developing incrementally makes it cheaper and easier to change the software as it is being developed.

  • Plan-driven incremental: decide the plan first, then follow it. The team decides in advance which features will be built in each increment.
  • Agile incremental: the early increments are identified, but the development of later increments depends on progress and customer priorities.

Each increment has some of the functionality the customer needs. Generally, the early increments include the most important or most urgently required functionality, so the customer can evaluate the system at a relatively early stage. (Slide 37 adds “Most important functionality” pointing at the initial version, and a “Functionalities” bar growing through the versions.)

Advantages (slide 38): 1. Costless: the cost of accommodating changing customer requirements is reduced; much less analysis and documentation has to be redone than with waterfall. 2. Customer feedback: easier to get; customers can comment on demonstrations and see how much has been implemented, and find it difficult to judge progress from design documents. 3. Deployment: more rapid delivery and deployment of useful software, even if all the functionality has not been included.

Drawbacks (slides 39–40): 1. The process is not visible: if the team does not report progress clearly, the manager may find it difficult to measure the project's status; managers need regular deliverables, and documenting every version of a fast-moving system is not cost-effective. 2. Regular change tends to corrupt its structure: adding features without organizing the code makes the software messy (a new feature may conflict with existing code), so further changes take more time and effort. Large systems need a stable framework or architecture, planned in advance rather than developed incrementally.

🧩 Reuse-oriented software engineering in detail (slides 16, 41–50)

This approach is based on the existence of a significant number of reusable components. A reusable component is a piece of software that already provides some required functionality and can be incorporated into another system. The development process focuses on integrating these components rather than developing them from scratch.

Informal reuse (slide 41): people who know of similar designs or code look for them, modify them as needed, and incorporate them. Example: your friend already wrote a student login page; instead of designing from scratch, you take the code, change it a little and use it, without a formal reuse process.

COTS (slide 42): sometimes the components are systems in their own right (commercial off-the-shelf systems), such as word processing (for writing documents) or a spreadsheet (for organizing data and calculations). COTS means software that is already available to buy or use, rather than created from scratch for your project.

The tutorial's six-stage reuse process rebuilt from T2 slide 42

Requirements specification

Beginning: decide what the system needs to do. This stage is comparable with other processes (waterfall, incremental).

Component analysis

Given the requirements specification, a search is made for components to implement it. Usually there is no exact match, and the components only provide some of the functionality required.

Requirements modification

The requirements are analyzed using information about the components discovered, then modified to reflect the available components. Where modifications are impossible, component analysis may be re-entered to search for alternatives. Example: the payment component supports only bank cards, but the university insists on bank cards and mobile wallets, so you go back to component analysis for a different payment component.

System design with reuse

The framework of the system is designed, or an existing framework is reused, organized around the reused components; new software may have to be designed where none are available. Example: you have Part A (student login) and Part B (online payment) but still need course registration, so you plan how to connect the parts and decide what else to build.

Development and integration

Software that cannot be externally procured/obtained is developed, and the components and COTS systems are integrated to create the new system. Here, integration may be part of development rather than a separate activity.

System validation

End: check that the system works correctly. Like the first stage, comparable with other processes; only the middle stages differ.

Advantage (slide 50): reducing the amount of software to be developed and so reducing cost and risks; faster delivery. Drawback: requirements compromises can't be avoided, and this may lead to a system that does not meet the real needs of users.

NOTE · TWO VERSIONS OF ONE PROCESS

Tutorial 2 uses this six-stage reuse process. Lecture 2 (§7) uses a newer five-stage version called integration and configuration. They describe the same idea; check which version your exam question names.

🧭 When to use what (slides 51–53)
  • For large systems, it makes sense to combine some of the best features of the waterfall and incremental models. You need information about the essential system requirements to design a software architecture that supports them. Sub-systems within a larger system may be developed using different approaches.
  • Waterfall is appropriate, in principle, only when the requirements are well understood and unlikely to change significantly during development. It is also suitable for systems where safety and security is critical. Parts of a system that are well understood can be specified and developed with a waterfall-based process, even if the whole project is not fully understood.
  • Incremental development, a fundamental part of agile approaches, is better than waterfall for most business, e-commerce, and personal systems, because you can build step by step and improve based on feedback. Parts that are difficult to specify in advance, such as the user interface, should always be developed incrementally.

Must-know points

  1. A software process is a structured set of activities to develop a software system. All processes involve specification, design and implementation, validation and evolution. 📄 S2
  2. A software process model is an abstract representation of a process, from a particular perspective. Process descriptions cover activities and their order, and may add products, roles, and pre- and post-conditions. 📄 S2–3
  3. Plan-driven: all activities planned in advance; progress measured against the plan. Agile: incremental planning; easier to change. Most processes mix both; there are no right or wrong processes. 📄 S4
  4. Three models: waterfall (plan-driven, separate phases), incremental development (interleaved; plan-driven or agile), integration & configuration (assembled from configurable components; plan-driven or agile). Most large systems combine all three. 📄 S6
  5. Waterfall: five phases; main drawback is accommodating change once underway. Only for well-understood requirements; mostly used for large systems engineering projects at several sites. 📄 S7–9
  6. Incremental development: cheaper change, easier customer feedback, faster useful delivery. Problems: the process is not visible; structure degrades without refactoring. 📄 S10–12
  7. Integration & configuration: reuse COTS application systems, object packages for component frameworks (.NET, J2EE) and web services; five key stages. Lower cost and risk, faster delivery; but requirements compromises and loss of control over reused elements. 📄 S13–17
  8. Change is inevitable. Cost of change = rework + new functionality. Reduce rework by change anticipation (prototyping) and change tolerance (incremental). Incremental delivery supports change avoidance and change tolerance. 📄 S19–21
  9. Prototypes are used in requirements engineering, design and testing; they bring five benefits; they focus on poorly understood, functional parts; and they should be thrown away (four reasons). 📄 S22–26
  10. Incremental delivery: prioritised increments, highest priority first, requirements frozen once an increment starts. Advantages: earlier value, early increments act as prototypes, lower failure risk, most testing for top services. Problems: shared basic facilities are hard to identify; clashes with procurement contracts; hard for replacement systems. 📄 S27–31

Lecture 3 · Requirements Engineering

Open full lecture →

Prof. Dr. Sherin Moussa · 34 slides · practice from Tutorial 2 (which tests Lecture 2's process models)

Must-know points

  1. Requirements engineering establishes the services a customer requires and the constraints under which the system operates and is developed. Process: elicitation and analysis → specification → validation; outputs: system descriptions, user and system requirements, the requirements document. 📄 S3–4
  2. Requirements range from abstract statements to detailed specifications because of their dual function: basis for a bid (open to interpretation) and basis for the contract (defined in detail). 📄 S5
  3. User requirements: natural language plus diagrams, written for customers. System requirements: a detailed structured document; may be part of the contract. Developers read only system requirements; client/contractor managers only user requirements. 📄 S6–8
  4. A stakeholder is anyone affected by the system with a legitimate interest: end users, system managers, system owners, external stakeholders. Mentcare: patients, doctors, nurses, receptionists, IT staff. 📄 S9–10
  5. Agile methods see detailed requirements as a waste of time; they use incremental RE and user stories. Practical for business systems; problematic for critical systems or several teams. 📄 S11
  6. Functional (services, reactions, behaviour; may say what not to do), non-functional (constraints; usually whole-system), domain (constraints from the domain of operation). 📄 S13–15
  7. Imprecise requirements are ambiguous (the Mentcare “search” example). Requirements should be complete and consistent, but in practice that is impossible. 📄 S16–17
  8. NFRs may be more critical than functional ones, may affect the whole architecture and generate functional requirements. Classes: product, organizational, external, each with sub-types. 📄 S18–22
  9. A goal is a general intention; a verifiable NFR uses a measure that can be objectively tested. Metrics cover speed, size, ease of use, reliability, robustness and portability. 📄 S23–25
  10. Requirements change (environment, payers ≠ users, diverse users). Requirements management plans identification, change management, traceability and tool support; change management runs problem analysis → change analysis and costing → change implementation. 📄 S27–32
